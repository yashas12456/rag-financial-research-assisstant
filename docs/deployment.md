# Deployment Guide

## Local development (without Docker)

**Backend:**
```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp ../.env.example ../.env   # then edit LLM_API_KEY etc.
# Start Postgres + Qdrant locally (e.g. via Docker) or point DATABASE_URL/QDRANT_URL
# at existing instances.
uvicorn app.main:app --reload --port 8000
```

**Frontend:**
```bash
cd frontend
npm install
npm run dev   # http://localhost:3000
```

## Docker Compose (recommended)

```bash
cp .env.example .env   # edit LLM_API_KEY at minimum
docker compose up --build
```

This starts, in order (via `depends_on` + healthchecks):
1. `postgres` (pgvector image, though we use Qdrant for vectors — Postgres
   here holds relational metadata)
2. `qdrant` (vector store)
3. `backend` (waits for both to report healthy)
4. `frontend`

Then visit `http://localhost:3000` (UI) or `http://localhost:8000/docs`
(interactive API docs, auto-generated by FastAPI).

## Environment variables

See `.env.example` for the full list with inline comments. At minimum you
must set:
- `LLM_API_KEY` — an Anthropic or OpenAI API key
- `LLM_PROVIDER` — `anthropic` or `openai`, matching the key above

Everything else has a sensible default for local/demo use.

## Database migrations

For simplicity, this project uses `Base.metadata.create_all()` at startup
(see `app/main.py`) rather than Alembic migrations, so it runs
friction-free out of the box. **For a real production deployment**, switch
to Alembic-managed migrations:

```bash
cd backend
alembic init alembic          # one-time
alembic revision --autogenerate -m "initial schema"
alembic upgrade head
```

and remove the `create_all()` call from `app/main.py`'s lifespan handler.

## Scaling considerations (see also interview_questions.md)

- **BM25 index**: currently rebuilt in-memory on every ingestion
  (`app/services/ingestion_service.py::rebuild_bm25_index`). This is fine
  for dozens–hundreds of documents but won't scale to millions of chunks.
  At that scale, swap in a persistent inverted-index engine
  (Elasticsearch, OpenSearch, or Tantivy) behind the same
  `BM25Index`-shaped interface.
- **Vector store**: Qdrant scales horizontally (sharding/replication) far
  past what a single-node deployment handles; see Qdrant's clustering docs
  for that path.
- **Embedding/reranking compute**: both currently run in-process on the
  API server. At higher throughput, extract them into a separate
  service/worker pool (e.g. behind a queue) so a burst of uploads doesn't
  block query latency, and so GPU instances (much faster for both models)
  can be provisioned independently of the API tier.
- **Rate limiting**: `RATE_LIMIT_PER_MINUTE` is defined in config as an
  extension point but not yet enforced in middleware. For production, wire
  in `slowapi` or an API-gateway-level rate limiter keyed by API key/IP.

## Security notes

- File uploads are validated by extension (`.pdf` only) and size
  (`MAX_UPLOAD_SIZE_MB`) before being written to disk — see
  `app/services/ingestion_service.py::validate_upload`.
- Uploaded files are stored under a randomly-prefixed filename
  (`uuid4()_original_name.pdf`) to avoid path traversal / overwrite issues
  from user-controlled filenames.
- No secrets are hardcoded anywhere in source; all come from environment
  variables (`app/core/config.py`).
- Unhandled exceptions never leak stack traces to the client — see
  `app/core/errors.py::unhandled_exception_handler`, which logs the full
  traceback server-side but returns a generic message.
- CORS is wide-open (`allow_origins=["*"]`) only when `ENV != production`;
  set explicit allowed origins before deploying publicly.
